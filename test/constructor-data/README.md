# Pyret constructor-data model, version 1

This is an **opt-in experimental Pyret adapter**, not a change to the existing
`genlayout` / `PyretDataInstance` path. It implements a structural data model
and tests inspection fidelity through Spytial's actual `JSONDataInstance`.
It does not use value skeletons. The older [reification evaluation](../reify-fidelity/README.md)
remains available to measure the existing importer separately.

## Supported value model

The model is the least set of finite values generated by:

```text
V ::= Integer(n)                          -2^31 <= n <= 2^31 - 1, exact
    | String(s)                           any finite UTF-16 string
    | Boolean(b)
    | Singleton(constructor-name)
    | Constructor(constructor-name, [(field-name, V), ...])
```

Fields are **ordered and named**, with distinct names within a constructor.
The empty field sequence is legal and differs from a singleton: `zero()`
is not `zero`. Names are taken from actual Pyret constructor metadata, not
from a registry of the particular datatypes in our test corpus.

For Pyret, this means finite, acyclic values made by `data` variants with
immutable constructor fields, using the runtime's default constructor printer.
Every constructor-field descendant must also be in the model. Shared subvalues
are allowed: the reachable structure may be a DAG, not only a tree.
Recursive, mutually recursive, and parameterized declarations are allowed;
membership depends on the actual field values, not on a static typechecker.
The test generators nevertheless respect their declared field types.

The primitive integer bound is an explicit first-version choice, **not** the
limit of Pyret numbers or of relational encoding. Fractions, roughnums, and
integers outside that interval are rejected rather than rounded. String data
is stored unescaped and untruncated; escaping happens only in the decoder.

Excluded at every constructor-field depth:

- References, mutable constructor fields, and cycles.
- Plain objects, tuples, arrays, functions, `nothing`, and opaque host values.
- Any value with an effective `_output` method, including built-in lists.
  A user-defined immutable `Chain` with default printing **is** included.

Ordinary attached methods do not disqualify a value: the default data printer
does not print them. The adapter traverses constructor fields, not arbitrary
additional object fields. It does not claim full object-field, method, brand,
nominal type identity, or executable-value preservation. Two datatypes whose
constructors have the same printed name need not be distinguished for this
observation. No globally bound constructor name is required by the decoder.

The relevant language abstraction is Pyret's
[`data` declarations](https://pyret.org/docs/latest/s_declarations.html), not an
officially named “Core Pyret” subset. The implementation follows the runtime's
`DefaultReprMethods.data` / `render-data` dispatch and `_torepr` string escaping
in `spyret-lang/src/js/base/runtime.js`. Custom `_output` dispatch is excluded
before any printer is called.

## Relational encoding

The payload consists solely of Spytial `atoms`, `relations`, and `types`.
No source expression, output string for a composite value, live object,
printer method, schema cache, or hidden reconstruction side channel is included.

| Item | Representation |
| --- | --- |
| Primitive | `CDInteger`, `CDString`, or `CDBoolean` atom; label carries exact leaf data |
| Singleton | `CDSingleton` atom; label is its constructor name |
| Constructor | `CDConstructor` atom; label is its constructor name |
| Root | One unary `cdRoot(value)` tuple |
| Arity | `cdArity(constructor, position-atom)` |
| Constructor field | `cdField(parent, position-atom, field-name-atom, child)` |
| Position / field name | `CDPosition` / `CDFieldName` atom with its value in the label |

Positions are zero-based. The arity allows a decoder to detect missing fields,
including a missing final field. A value atom retains its runtime object identity
within one export; repeated edges to that object use the same ID. Equal but
distinct constructor objects are not merged. Primitive occurrences can have
separate atoms. IDs have no meaning or stability across exports.

The position column preserves repeated arguments under relational set semantics.
The type tag prevents `"5"` from being confused with `5`, and the root is explicit
even for a primitive or singleton. Enumeration order of atoms, relation records,
and field tuples carries no information.

## Adapter and direct decoder

The module [pyret-constructor-datum.js](../../src/web/js/pyret-constructor-datum.js)
exports `exportValue(runtime, value)` and `inspectDatum(datum)`. In a browser,
loading it as a script exposes `PyretConstructorDatum`; CommonJS consumers can
require it. It is not loaded into the editor automatically by this PR.

```javascript
const payload = PyretConstructorDatum.exportValue(runtime, value);
const received = new spytialcore.JSONDataInstance(payload);
const text = PyretConstructorDatum.inspectDatum(received);
```

The adapter reads `isDataValue`, `$name`, `$arity`,
`$constructor.$fieldNames`, `$mut_fields_mask`, and `dict`. These are runtime
implementation details, so a Pyret upgrade needs the live-runtime tests below.
Unsupported values throw `UnsupportedValue` with a reason and field path;
they never produce a partial successful export.

The decoder uses only atom types/labels and relation tuples. It does **not**
evaluate Pyret source, call `torepr`, or need the input declaration/prelude.
It rejects malformed rooted structures (including missing positions, duplicate
fields, dangling references, and cycles). It is not a general-purpose validator
for arbitrary Spytial data. Both traversal and rendering currently use the JS
call stack: extremely deep finite inputs can exceed implementation resources.

## Fidelity argument and its limits

The intended property for supported values is:

```text
inspectDatum(JSONDataInstance(exportValue(runtime, v))) = torepr(v)
```

The reference is specifically Pyret `_torepr`, not a graphical REPL renderer
or the command-line `$cli` renderer.

For the abstract model, fidelity follows by structural induction on the value's
finite unfolding. The leaf encodings retain the data required by the primitive
printer. A singleton retains its name and singleton tag. A constructor retains
its name and every child at its argument position; applying the induction
hypothesis to those children and joining with Pyret's constructor punctuation
produces the same output. Sharing does not affect this default acyclic output.

This is an argument about the specified encoding, **not** a machine-checked
proof of the JS implementation or of Pyret's runtime. Finite tests below check
that the implementation agrees with the real runtime. They do not prove the
property for every value or declaration admitted by the model.

## Tests and reproducibility

```bash
npm run test:constructor-data:unit
npm run test:constructor-data
```

The full suite requires built `build/web`, Chrome/Chromium, and network access
to the editor's pinned Spytial bundles. It reuses the existing fidelity harness's
server/browser setup. `BASE_URL`, `PORT`, `CHROME_BINARY`, and `SHOW_BROWSER`
have the same meanings as in the older harness. On Apple Silicon, use native
ARM Node/Chrome; an Intel Node can launch Chrome under slow Rosetta emulation.

`CONSTRUCTOR_SEED` defaults to 1. `CONSTRUCTOR_RUNS` is a positive number of
samples **per family**, default 30. `CONSTRUCTOR_REPORT` overrides
`build/constructor-data-report.json`.

The live test pipeline is:

```text
same live value -> runtime _torepr ---------------------------> A
                -> new constructor adapter -> JSON
                   -> Spytial JSONDataInstance -> JSON
                   -> direct decoder in Node ----------------> B
```

Each case starts fresh Pyret interactions with its declaration prelude, rather
than accumulating compiler environments across samples. The value is evaluated
once. Export happens before reference printing. The
Spytial JSON importer receives only the serialized payload, with default
normalization. The resulting datum is serialized again, its enumeration order
reversed, and decoded in Node, which has no Pyret runtime. The decoder function
is passed only the datum; it does not receive A, the expression or a schema.

`corpus.js` defines the precise finite experiment:

- 26 positive fixed cases: integer endpoints, escaping/Unicode, both base forms,
  order, multiplicity, sharing versus equal distinct values, ordinary methods,
  and values from recursive, mutually recursive and parameterized declarations.
- 17 negative cases with exact rejection reasons, including a throwing custom
  printer that must not run. Compile errors are test failures, not rejections.
- Five type-directed generated families: `Tree` (depth 4), `Expr` (depth 3),
  string `Chain` (length 0-6), mutually recursive `Rose`/`Forest` (rose depth 3,
  0-3 children per node), and primitives. Integers span the declared domain;
  generated strings contain 0-12 arbitrary UTF-16 code units.
- Ten generated datatype declarations, each with a singleton, a zero-argument
  constructor, and 1-4 additional variants of arity 1-4. Fields are selected
  from `Number`, `String`, `Boolean`, and self-recursion. Every variant gets a
  witness, plus ten generated values per declaration (depth at most 3).
  These samples use integers -999..999 and three fixed string literals.
- Unit tests for the representation contract, malformed data, and 1,000
  generated string round trips, including decoder replay in a fresh JS realm
  supplied only the module and serialized datum.

The JSON report retains all source expressions, declarations, A/B strings,
exported and Spytial-received data, expected rejections, seed, and runtime
environment versions. A partial, empty, mismatching, or unexpectedly failing
run cannot report conformance. Reports are generated artifacts under `build/`,
not committed fixtures.

## Verified experiment

On 2026-09-12, with native ARM Node 22.22.2, Chrome 152 and the editor's pinned
spytial-core 4.4.3, the default seed-1 experiment produced **319 exact matches**
and **17 expected rejections**. The 319 positive values comprise 26 fixed cases,
150 type-directed samples, 43 generated-schema variant witnesses, and 100
generated-schema samples. These counts describe this finite run, not an
exhaustive validation of the abstract model.

An independent seed-2 run produced 320 exact matches and the same 17 expected
rejections (44 generated-schema witnesses rather than seed 1's 43). Both seeds
pass the full 70-test constructor-data suite.
